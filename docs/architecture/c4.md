# bk-agent-stack-orchard — C4 diagrams

These diagrams show the three C4 views of [`workspace.dsl`](workspace.dsl), which is the model.
The workspace also holds the same elements and relationships as text. The draw.io sources of the
diagrams are in [`docs/diagrams`](../diagrams). A change to the model needs the matching change to
the drawing in the same pull request. `mise run diagrams` exports the drawings to SVG.

## Level 1 — System context

![System context of bk-agent-stack-orchard. The pipeline author uploads pipelines to Buildkite, and
reads job results and stack notifications there. The fleet operator configures profiles and
operates the Mac hosts of the stack. The fleet operator also reads metrics, traces, and logs in the
telemetry backend. Kubernetes runs and probes the controller and the Orchard controller. The stack
gets scheduled jobs from Buildkite, and runs and reports jobs over HTTPS/JSON. It pulls VM images
from the OCI registry over the OCI Distribution API. It gets source code and cache entries from the
source hosts and remote caches over HTTPS. It exports metrics, traces, and logs to the telemetry
backend over OTLP. Buildkite, the OCI registry, the source hosts and remote caches, Kubernetes, and
the telemetry backend are external systems.](../diagrams/c4-system-context.svg)

## Level 2 — Containers

![Containers of bk-agent-stack-orchard: the controller, the Orchard controller, the Orchard state
store, the Orchard worker, Tart, and the temporary job VM. The controller lists and reserves jobs,
gets tokens and job states, finishes jobs, and sends notifications through the Stacks API of
Buildkite. It lists workers and VMs, creates and deletes VMs, and reads VM events through the
Orchard REST API. The Orchard controller reads and writes state in the state store. The Orchard
worker registers with the Orchard controller over outbound gRPC, gets VM assignments, and reports
VM status. The worker controls Tart through its CLI, and runs the startup script in the job VM
through the Tart guest agent. Tart pulls VM images from the OCI registry, and runs the job VM with
Virtualization.framework. The job VM acquires its job from the Agent API of Buildkite, and sends
logs, artifacts, and the result. It gets source code and cache entries through Softnet. The fleet
operator configures profiles through the deployment platform, and installs the worker with
Ansible. The fleet operator also reads metrics, traces, and logs in the telemetry backend.
Kubernetes runs and probes the controller, and runs the Orchard controller. The controller, the
Orchard controller, and the worker export telemetry to the telemetry backend over OTLP. The job VM
exports agent traces when the profile enables it.](../diagrams/c4-containers.svg)

## Level 3 — Controller components

![Components of the controller. The fleet operator supplies the configuration file and secrets to
Configuration. Kubernetes probes liveness and readiness on the Health server over gRPC.
Configuration gives intervals, limits, and timeouts to the Tick loop, and profiles to the Matcher.
The Health server reads the last synchronization times from the Tick loop. The Tick loop registers
and deregisters the stack through Stack, and reads scheduled jobs and dispatch_paused from the
Poller. It refreshes Inventory and JobStates. It runs the Reaper for each owned VM, Admission with
fresh data, and the Launcher with admitted and unmatched jobs. Admission matches jobs to profiles
with the Matcher, and reads workers and VMs from Inventory. The Reaper reads owned VMs from
Inventory and job states from JobStates. Stack, the Poller, JobStates, the Reaper, and the Launcher
use the Stacks client, which calls the Stacks API of Buildkite. Inventory, the Reaper, and the
Launcher use the Orchard client, which calls the REST API of the Orchard controller. Telemetry
exports metrics, traces, and logs to the telemetry backend over OTLP.](../diagrams/c4-controller-components.svg)
